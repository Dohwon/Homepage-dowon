# Project Atlas 캡처 및 의미형 System Map 개편 설계

## 1. 목적

Project Atlas의 프로젝트 페이지를 처음 보는 사람이 구현 결과와 의사결정 흐름을 이해할 수 있도록 다음을 개선한다.

- 실제 구현 화면이 있는 프로젝트는 공개 검토된 캡처를 프로젝트 문서 안에 보여준다.
- 캡처는 프로젝트 제목 영역에 고정하지 않고 `Decisions` 문서 아래에 배치한다. 따라서 다른 탭으로 이동할 때 캡처가 반복해서 화면을 차지하지 않는다.
- System Map은 모든 프로젝트에 같은 입력-처리-결과 레이아웃을 적용하지 않고, 프로젝트의 핵심 관계를 표현하는 유형별 지도로 만든다.
- 프로젝트 폴더와 프로젝트 메모리의 변경은 기존 일일 동기화가 감지하고, 공개 승인 경계를 유지한다.

## 2. 범위

### 포함

- 캡처 메타데이터와 공개 번들 스키마
- 프로젝트 화면의 캡처 위치 및 캡처 목록 렌더링
- 토닥을 포함한 공개 프로젝트의 실제 구현 화면 검토 등록
- 유형별 System Map 데이터와 SVG 표현 규칙
- 새 프로젝트 및 프로젝트 메모리 변경 감지 테스트
- Railway 재배포 및 공개 API 검증

### 제외

- Codex 대화 원문 공개
- 프로젝트 폴더의 모든 이미지 자동 공개
- 근거가 없는 프로젝트 설명이나 캡처 자동 생성
- 기존 `data/blog-posts.json`, `data/site-content.json`의 사용자 변경 내용

## 3. 공개 경계

공개 대상은 프로젝트 안에서 명시적으로 검토된 자료로 제한한다.

```text
project_memory/project-atlas/
  captures.yaml          # 공개할 화면 목록과 설명
  captures/              # 목록에 등록된 이미지 원본
  cover.png              # 기존 단일 캡처 호환용
  article.yaml           # 공개 글
  system-map.yaml        # 공개 지도 데이터
  system-map.svg         # 검증된 지도 SVG
```

- `captures.yaml`에 등록된 파일만 공개 번들로 복사한다.
- 경로는 프로젝트 루트 밖으로 나갈 수 없고 symlink를 허용하지 않는다.
- 이미지 타입, 크기, 파일 signature와 privacy gate를 검사한다.
- 기존 `cover.png`는 당장 깨지지 않게 읽되, 새 등록은 `captures.yaml`을 정본으로 사용한다.
- 실제 화면이 없거나 공개 검토되지 않은 프로젝트는 캡처 없이 공개할 수 있다.
- 디자인 참고자료, 로고·아이콘, 테스트 실패 캡처는 명시적으로 등록하지 않는 한 공개하지 않는다.

## 4. 캡처 UX

- 프로젝트 제목·태그·본문 상단에는 캡처를 렌더링하지 않는다.
- `Decisions` 탭의 의사결정 글이 끝난 뒤 `구현 화면` 섹션으로 캡처를 렌더링한다.
- 캡처가 여러 장이면 프로젝트가 드러나는 대표 화면을 첫 장으로 두고, 나머지는 결정과 연결되는 순서로 보여준다.
- 각 캡처에는 짧은 설명과 화면 역할을 표시한다.
- `Overview`, `System Map`, `Evidence`, `Build Timeline` 탭에는 캡처를 중복 표시하지 않는다.
- 캡처가 없으면 빈 이미지 영역을 만들지 않는다.

## 5. 의미형 System Map

지도는 노드 수를 맞추기 위한 장식이 아니라, 프로젝트를 설명하는 핵심 관계를 표현한다. 각 프로젝트는 다음 유형 중 하나를 선택하며, 한 유형의 노드 수와 단계 수를 고정하지 않는다.

| 지도 유형 | 보여줄 관계 | 대표 프로젝트 |
| --- | --- | --- |
| 버전 로드맵 | 이전 버전의 한계가 다음 버전의 기능·정책으로 이어지는 관계 | 지도 기록 다이어리 v1-v4 |
| 상태 전이 | 사용자·시스템 상태와 전이 조건, 실패·복구 경로 | Todack, AI Office |
| 데이터 흐름 | 원천 데이터가 검증·변환·저장·출력으로 이어지는 경로 | 로그 분석, 테스트셋 |
| 에이전트 오케스트레이션 | 라우터, 전문가, 평가자, fallback의 책임 경계 | A2A, MoE Routing |
| 평가 루프 | 기준셋, 실행, 판정, 회귀 반영의 순환 | Prompt Evaluation, LLM Tester |
| 서비스 경계 | 사용자 표면, 서버, 저장소, 외부 서비스와 보안 경계 | Memento Mori, Polite Message |

각 노드는 다음 정보를 가진다.

- 무엇인지: 노드의 역할
- 왜 필요한지: 프로젝트 문제와 연결된 설명
- 어떤 결과를 냈는지: 결정 또는 전환의 결과

각 흐름은 단순한 `next`가 아니라 `원인`, `선택`, `제약`, `복구`, `폐기` 중 하나의 의미를 갖고, 설명 문장으로 결정의 이유를 전달한다. Decisions 탭은 상세한 서술을 담당하고, System Map은 그 서술 사이의 구조적 관계만 보여준다.

## 6. 동기화와 새 프로젝트

- 일일 runner는 `projects/`와 `projects/finish/`의 바로 아래 폴더를 탐색한다.
- 새 폴더, 프로젝트 메모리, 문서와 소스의 변경을 source manifest로 감지한다.
- 공개 profile과 article이 없는 새 폴더는 발견 사실과 보류 사유만 로그에 남기고 공개하지 않는다.
- 공개 profile, article, captures, system map이 모두 검증되면 전체 public bundle을 재생성하고 Railway 배포 저장소에 반영한다.
- 대용량 생성물·의존성 디렉터리는 동기화 성능을 위해 해시 대상에서 제외하며, 공개 자료는 `project_memory/project-atlas/`에 둔다.

## 7. 검증 기준

1. 토닥의 실제 구현 화면이 공개 검토 목록에 등록되고 `Decisions` 탭 아래에서만 보인다.
2. 기존 7개 캡처 프로젝트가 회귀 없이 계속 표시된다.
3. 캡처가 없는 프로젝트에는 빈 이미지 영역이 없다.
4. 전체 공개 프로젝트의 System Map이 유형별 데이터와 SVG를 사용하고, 특정 노드 수를 강제로 맞추지 않는다.
5. 지도 노드와 흐름에 프로젝트별 설명과 결정 근거가 들어간다.
6. 새 프로젝트 폴더 생성, `project_memory` 변경, 캡처 추가가 일일 runner의 affected 목록에 나타난다.
7. Worker, Node, SVG·공개 번들 검증을 통과한다.
8. Railway의 `/`, `/api/health`, `/api/atlas/bootstrap`와 캡처 API가 정상 응답한다.

## 8. 리스크와 대응

- **잘못된 이미지 공개**: 목록 기반 등록과 privacy gate로 자동 후보 공개를 차단한다.
- **캡처가 글을 가림**: Decisions 탭 내부의 문서 끝에 배치하고 다른 탭에서는 렌더링하지 않는다.
- **지도 유형이 이름만 달라짐**: 유형별 필수 관계와 프로젝트별 서술 검토를 테스트 및 샘플 QA에 포함한다.
- **새 프로젝트가 자동 공개되지 않음**: 발견 로그에 보류 상태를 남기고 필요한 정본 파일 경로를 문서화한다.
- **Railway 환경 변수 누락**: 공개 읽기 경로와 관리자 인증 경로를 분리해 검증하고, 인증 미설정은 배포 결과에 명시한다.
